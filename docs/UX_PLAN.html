01

Executive Design Direction

The mockups establish a strong visual direction. The gap between them and the current implementation is not conceptual—the right information is on each page—but one of execution quality: typography scale, spatial rhythm, component polish, interaction states, and the sense of confidence a manager feels when the application loads.

The mockups look like a product someone paid for. The current implementation looks like the engineering prototype behind it. Closing that gap is the work.

What the gap consists of

  • Brand presence. The mockups show the HungerRush logo mark and wordmark in the sidebar, with "CADENCE" as a sub-brand in teal. The current sidebar shows only "CADENCE" in white text—no logo, no brand hierarchy.
  • Typography scale. The current implementation uses a narrow range of sizes (text-sm / text-xs / text-xl) applied somewhat uniformly. The mockups use a more deliberate hierarchy: large greeting headings, clear section labels in uppercase tracking, well-sized data figures.
  • Spatial rhythm. The current p-8 content padding is uniform and generous but the internal spacing within sections is tight and inconsistent. The mockups have more breathing room between sections and more compact internal density—the opposite pattern.
  • Component refinement. The current StatCards, filter pills, pagination, and table rows are functional but lack the visual weight and polish of the mockup equivalents. The mockups' status summary cards have colored left-accent icons with distinct backgrounds; the current ones have smaller icons with less visual separation.
  • Interactive states. The current implementation has minimal hover states (underlines on links, background changes on nav items). The mockups imply richer interaction: hover rows in tables, hover elevation on cards, clickable metric rows with drill-down.
  • No dark mode. Tokens are declared but no dark palette exists.

Design stance

The direction is right. This is not a redesign. It is a refinement pass—promoting the existing prototype to the visual quality the mockups promise, while correcting specific layout and interaction decisions that won't hold up in production use.

02

Product UX Principles

These principles should govern every design and implementation decision. They are derived from PRODUCT.md but sharpened for the frontend.

1. The manager's time is the interface

Every element exists to save a manager time before a conversation. If something doesn't contribute to the question the page answers, it creates cognitive load that slows the manager down. The default should always be remove, not add.

2. Briefing, not dashboard

Dashboards show everything. Briefings show what matters. Home and 1:1 Prep are briefings—they should feel editorial, with clear hierarchy and narrative flow. Team and Employee are analytical—they should feel efficient and scannable. None of the four should feel like a reporting portal.

3. Status through form, not just color

A manager glancing at the Team page should be able to identify who needs attention from the shape of the row, not only from a color badge. Size, weight, icon presence, and position all carry status information.

4. Progressive disclosure as navigation

Home summarizes. Team compares. Employee explains. 1:1 Prep distills. Each page is a zoom level. The manager drills in when they need more; they should never need to drill in to understand the summary.

5. Data honesty over visual comfort

A missing value is not zero. A stale sync is not fresh data. The UI must communicate these states without making the manager anxious. Calm design, honest data.

6. Metric-agnostic layouts

The UI must work equally well whether a team has 3 metrics or 8, whether the metrics are percentages or durations or counts. No layout should depend on a specific metric count or type.

03

Home Experience

Question: "What happened this week that I need to know?"

Current state

The current Home page has the right sections: greeting, stat cards, needs-attention items, improvements, upcoming 1:1s, and team performance tables. The information hierarchy is correct. The problems are visual polish and density calibration.

Keep

Time-of-day greeting with the manager's name. Sets a personal, calm tone. The mockup does the same.

Keep

4-stat summary row (Employees, On Track, To Watch, Needs Attention). The mockup validates this layout. It's the right opening signal.

Change

Stat cards need more visual weight. The mockup shows each stat card as a distinct bordered box with a colored status icon on a tinted background circle. Current StatCards feel lighter and less scannable. Match the mockup's treatment: larger numbers, clearer icon containers, subtle status-colored icon backgrounds.

Change

Content width. Current max-w-5xl (64rem) is narrower than the mockup suggests. The Home page should use a wider container (around 72rem / max-w-6xl) for the 3-column layout to breathe. The mockup clearly has more horizontal room.

Change

"Needs attention" and "Improvements" are side-by-side columns in the mockup, not stacked. The mockup uses a clear two-column split within the left 2/3 of a 3-column grid. Current implementation nests them in md:grid-cols-2 lg:col-span-2 which works, but the visual treatment needs polish: the mockup uses section headers in red/teal uppercase with employee avatar cards, not just plain Card components with alert-triangle icons.

Add

Period navigation. The mockup shows left/right arrows and a date range display for navigating between weeks. The current implementation is locked to the current week with no way to look back. Add a simple prev/next week navigation.

Add

Employee avatars in the attention/improvement cards. The mockup shows face photos (or avatar fallbacks) next to each employee name. This creates a human connection the icon-only current version lacks. Add Avatar components to these cards.

Change

Team Performance table styling. The mockup shows status badges (colored pills) in the performance table and more prominent metric sparklines. The current table is plain text with small sparklines. Add StatusBadge for the status column and increase sparkline width.

Information hierarchy (recommended)

  1. Greeting + period + freshness—one line of orientation
  2. Status distribution cards—four stat boxes, always visible
  3. This Week (attention + improvements) + Upcoming 1:1s—the core briefing, 3 columns
  4. Team Performance summary table—the metrics context, scrollable if needed

Loading state

Show skeleton cards for the stat row immediately. Stream the briefing content below as data resolves using Suspense boundaries. The manager should see the page structure within 200ms; content fills in progressively.

04

Team Experience

Question: "How is everyone doing?"

Current state

The current Team page renders each team as a separate section with a TeamRosterTable. The table has filter chips, search, pagination, and the right columns. The main gaps are: no team-level summary stats above the table, no filter dropdowns for team/period/view selection (the mockup shows all four), no "Metrics View" alternate tab, and no Export button.

Keep

Filter pill chips (All, Improving, Declining, Needs Attention, No Change). The mockup has the same pattern. Keep the aria-pressed attribute.

Keep

Table columns. Employee (avatar + name + title), Status, Key Change, This Week, Trend sparkline, 1:1 Upcoming, Action arrow. This matches the mockup closely.

Add

Team summary bar above the table. The mockup shows a horizontal row of colored stat cards (Employees, On Track, Watch, Needs Attention) plus a "Team Trend (Overall)" indicator. This is the same pattern as Home's stat row. Add it.

Change

Simplify the mockup's filter bar. The mockup shows 4 dropdown selectors (Team, Period, View, Filter) plus search. This is overbuilt for the pilot's two 12-person teams. Start with: a Team selector (only if the manager has multiple teams), the status filter chips, and search. Period and View toggles add later once there's user demand. Don't build UI for hypothetical use cases.

Change

Table row hover state. The mockup implies rows are clickable (arrow button on the right). Add a subtle background highlight on hover for the entire row to signal interactivity, not just the arrow button.

Change

Avatar size. Current avatars are 28px (h-7 w-7). The mockup shows slightly larger ones (~32-36px) with more visual presence. Increase to h-8 w-8.

Defer

"Metrics View" alternate tab and Export button. The mockup shows these but neither adds value for the pilot with its two small teams. These are real features but belong after the pilot proves the core flow. Don't build them now.

Key interaction: drill-down

Clicking any employee row (not just the arrow) should navigate to their Employee page. The entire row should be a link target. The arrow button should navigate to 1:1 Prep for that employee. These are two different destinations—make the distinction clear through placement and labeling.

Decision point

Should clicking a Team row go to Employee or 1:1 Prep? The mockup's arrow goes to Prep. But the product's journey is Home → Team → Employee → Prep. Recommendation: row click goes to Employee, arrow button goes to Prep. This matches the natural drill-down flow and avoids skipping the analytical layer.

Employee Experience

Question: "What's actually going on with this person?"

Current state

The Employee page is the densest of the four and has the most content. The current implementation is a single-column layout at max-w-3xl (48rem), which stacks everything vertically. The mockup shows a wider two-column layout with "What Changed" and "Performance Metrics" side by side, and "Historical Performance" and "Context" side by side below that.

Change

Widen to two-column layout. At max-w-5xl+, use a 2-column grid for the metrics content area. Left column: What Changed + Historical Performance chart. Right column: Performance Metrics table + Context tabs. The mockup's side-by-side layout reduces scrolling and lets the manager scan related information simultaneously.

Keep

Executive summary card. The narrative text with inline stat figures is effective. Both mockup and implementation agree here.

Change

Period selector. The mockup shows 4 options (This Week, Last Week, Last 4 Weeks, Last 12 Weeks) plus a calendar icon. The current implementation only has This Week / Last Week. Extend to 4 options. The longer periods should aggregate metrics, not just show a single week.

Add

Metric selector for the history chart. The mockup shows a dropdown to choose which metric's history to view. The current implementation always shows the primary metric. Add a <select> (or a small dropdown) to let the manager pick any of their metrics for the chart. This is a high-value, low-complexity addition.

Change

Context section density. The current context section has a border around the tabs area that feels heavy. The mockup integrates context more naturally into the page flow with tab triggers that look like inline navigation, not a bordered container. Match the mockup: tab triggers as underline-style text tabs, content flows directly below without an enclosing border.

Add

Provenance footer. The mockup shows Employee ID, Hire Date, Data Sources, and Last Updated in a subtle footer bar. The current implementation has data sources and freshness but not Employee ID or Hire Date. Add these—they're useful for the manager when cross-referencing with HR systems.

Keep

"Prepare 1:1" CTA in the header. Both mockup and implementation place this prominently. It's the primary action from this page.

Chart interaction

The MetricHistoryChart is currently pure SVG with no interactivity. The mockup shows a tooltip on hover showing the period dates and value. Add a hover tooltip using a lightweight approach (CSS + data attributes or a tiny client component that tracks mouse position). Do not add a charting library for this.

06

1:1 Preparation Experience

Question: "What do I need to know before I meet this person?"

This is the most important page. It's the page that directly saves the manager time. If only one page gets the visual refinement pass, it should be this one.

Current state

The current implementation has the right content sections in the right order. The main issue is that it feels too similar to the Employee page—same density, same visual treatment. The mockup makes the 1:1 Prep page feel distinctly calmer and more meeting-focused.

Change

Visual tone shift. The 1:1 Prep page should feel like a printed briefing document, not a data page. Use slightly larger body text (15px instead of 14px), more generous section spacing, and a narrower overall measure. The mockup achieves this through whitespace and card-based sections with clear borders.

Change

Three-column middle section. The mockup uses a 3-column layout: What Changed | What to Recognize + What to Discuss | Previous Context. The current implementation uses 2 columns. The 3-column layout gives more breathing room and separates the recognition/discussion sections from the metric changes. However, on common 1366px laptop screens, three narrow columns may feel cramped. Recommendation: use 2 columns at md (What Changed + Recognize/Discuss on left, Context + Checklist on right), and let it stretch to 3 at xl if the viewport supports it.

Keep

"At a Glance" summary card with the trend icon. The mockup's green trend-arrow icon in a tinted circle is a nice touch. It gives instant visual confirmation of the employee's overall direction. Replicate this.

Change

Meeting prep checklist. The current checklist has 2 pre-checked disabled checkboxes and 1 interactive one. This is decorative, not functional. The checkboxes don't persist and can't be shared. Either remove the checklist entirely (it's cargo-cult meeting prep) or make it genuinely useful by persisting checkbox state to localStorage so the manager can track their own prep progress within a session. Recommendation: keep it, persist to localStorage, and add a 4th item "Review action items from last meeting."

Change

Suggested questions styling. The current italic + muted color treatment makes suggested questions feel like an afterthought. The mockup wraps them in cards with a teal icon, giving them more visual weight. Find a middle ground: use a subtle tinted background section (not full cards per question), with a clear "(Optional)" label so the manager doesn't feel obligated.

Add

Header "Open in Rippling" button. The mockup places this prominently in the page header alongside a more-actions menu. Currently it's a text link in the footer. Move it up. When RIPPLING_MANAGER_URL is set, show it as a teal-outlined button in the header area.

Strongest element

The mockup's 1:1 Prep page is the single strongest design in the set. It successfully makes a data-dense application feel like a calm meeting briefing. The information architecture—At a Glance, then Changes, then Recognition, then Discussion, then Context, then Questions, then Checklist—follows the natural flow of a manager preparing for a conversation. Preserve this flow exactly.

Reusable Component System

The current component inventory is solid: 13 domain components + 7 UI primitives. The mockups suggest a few additions and refinements.

Components to refine

StatCard

Increase the visual weight. The mockup shows: a circular colored icon container (~40px), a large number (28-32px, font-weight 700), a label below, and a detail line. The current StatCard is smaller and lighter. Match the mockup's proportions.

StatusBadge

The current badge maps 8 status values to labels and colors. This is correct. The mockup's badges are compact rounded pills with tinted backgrounds. Verify the pill sizing is consistent—padding should be px-2 py-0.5 with text-xs font-medium. The current implementation appears correct but verify optical alignment.

TrendSparkline

Increase default width from 72px to ~96px. The mockup shows wider sparklines with more visual presence. The current 72x24 is too small to communicate meaningful trends with only 4 data points.

MetricHistoryChart

Add hover interaction (tooltip showing period + value). Add metric selector prop so the parent can switch between metrics. Keep the pure-SVG approach but wrap in a thin client component for mouse tracking.

Components to add

TeamSummaryBar

A horizontal bar showing the status distribution for a team (employees count, on track, watch, needs attention) plus an overall trend indicator. Used on both Home and Team pages. Renders as a row of StatCards or compact stat cells inside a bordered container.

PeriodSelector

A segmented control or button group for selecting time periods (This Week, Last Week, Last 4 Weeks, Last 12 Weeks). Used on Employee and potentially Home. Server component with URL-based state (?period= query param).

WeekNavigator

Left/right arrows + date range display for navigating between weeks. Used on Home. Manages state via URL query params.

EmployeeCard

A compact card showing employee avatar, name, a brief reason text, a status badge or trend sparkline, and optionally a link-out. Used in the Home page's attention/improvement sections. Currently this is inlined as JSX in the Home page; extract it.

MetricChangeRow

A single metric's week-over-week change: name, previous value, arrow, current value, trend indicator. Used on both Employee and 1:1 Prep pages. Currently duplicated in both pages' JSX; extract it.

ContextTimeline

The timeline-style context list with left border and icon dots. Used on 1:1 Prep. Currently inlined; extract for reuse on Employee's context overview tab.

Design Token System

The current token system is well-structured: OKLCH colors, CSS custom properties mapped through Tailwind v4's @theme inline. The foundation is correct. Refinements needed:

Typography tokens to add

Token Value Use
--text-page-title 24px / 600 Page headings (h1)
--text-section-title 11px / 600 / uppercase / 0.06em tracking Section labels ("WHAT CHANGED THIS WEEK")
--text-stat-value 28px / 700 Large numbers in stat cards
--text-body 14px / 400 Default body text
--text-small 13px / 400 Secondary text, table cells
--text-caption 12px / 500 Timestamps, metadata

Spacing tokens to add

The current system relies on Tailwind's default spacing scale (p-8, gap-6, space-y-3, etc.). This works but creates inconsistency across pages. Define named section-level spacing:

Token Value Use
--space-page-padding 24px (lg: 32px) Main content area padding
--space-section-gap 32px Between major page sections
--space-block-gap 16px Between items within a section
--space-inline-gap 8px Between inline elements

Color refinements

The current palette is good. Two additions:

  • A "surface-raised" token for elements that sit on top of the card surface (like hover states or nested containers). Currently the only distinction is --card (white) vs --background (near-white). A third level helps with hover states on cards.
  • Dark mode palette. The @custom-variant dark declaration exists but has no token overrides. Define a full dark palette: navy-900 background, slightly elevated card surfaces, desaturated-but-legible status colors. This is a production app managers may use in the evening; dark mode is real, not decorative.

Border radius

The current 0.5rem (8px) radius is slightly large for a professional tool. The mockups appear to use a smaller radius (~4-6px). Recommend --radius: 0.375rem (6px) for cards and containers, keeping rounded-full for pills and avatars.

Motion and Interaction System

Where motion should exist

  • Page transitions: None. Server Component pages render immediately; adding cross-page transitions adds complexity for no manager benefit. Let the browser handle paint.
  • Hover states: All interactive elements should have a 150ms ease-out transition on background-color and color. Table rows should have a subtle bg-muted/50 hover. Card-style list items should have a very subtle shadow lift or border-color change.
  • Focus states: A 2px teal ring offset by 2px. Visible on keyboard focus only (:focus-visible), not on click.
  • Filter chip selection: 150ms background-color + border-color transition. No bounce or spring effects.
  • Accordion/tab switching: Content should appear instantly. No slide or fade—instant swap is faster and respects the manager's scanning speed.
  • Tooltip appearance: 100ms fade-in after a 300ms hover delay. Prevents flicker when the mouse crosses interactive elements.
  • Loading skeletons: A single animate-pulse at 2s duration is correct. No shimmer effects (they draw the eye to loading rather than content).

Where motion should not exist

  • No page-load animations (fade-in-up, staggered reveals). This is a work tool, not a marketing site.
  • No counter-up animations on stat numbers. They slow down the manager's read.
  • No chart draw animations. The chart should be there when the section renders.
  • No skeleton-to-content crossfade. The skeleton simply disappears and the content is there.

Reduced motion

Wrap all transitions in @media (prefers-reduced-motion: no-preference). Under reduced motion, all state changes should be instantaneous. The animate-pulse on skeletons should use a static gray background instead.

Responsive Strategy

The product is desktop-first. The primary viewport is a corporate laptop: 1366x768 to 1920x1080. But a manager checking Cadence on an iPad or from their phone before a meeting is a realistic scenario.

Breakpoints

Breakpoint Target Behavior
< 768px Phone / small tablet Sidebar collapses to a hamburger menu. Content is single-column. Tables become card lists. Charts shrink. Period selectors become a dropdown.
768-1024px Tablet / small laptop Sidebar stays visible but narrower (48px icon-only, expandable on hover). Content uses 2-column layouts where the mockup shows 2 or 3.
1024-1440px Common laptop Full layout, sidebar expanded. Content areas at comfortable width. This is the primary target.
> 1440px Large monitor Content remains max-width constrained (72rem). Whitespace fills sides. No stretching to fill.

What collapses on small screens

  • Stat cards: 4-column → 2-column grid
  • Attention/Improvements: side-by-side → stacked
  • Team Performance table: horizontal scroll with sticky first column
  • Employee 2-column layout: stacked, with "What Changed" first
  • 1:1 Prep columns: stacked
  • Sparklines in tables: hidden below md
  • Period selector: segmented control → compact dropdown

What never collapses

  • The greeting and stat summary on Home
  • Employee name, status, and executive summary
  • 1:1 Prep "At a Glance" and "What to Discuss" sections
  • Navigation (just changes form)

Accessibility Strategy

Accessibility is already partially in place: aria-pressed on filter chips, aria-current on pagination, Radix tabs with real ARIA roles, sr-only captions on tables, and role="status" on empty states. What's missing:

Heading hierarchy

Currently inconsistent. Some pages use <h1> for the page title and <h2> for sections, but BriefingSection uses bold text, not a heading element. Standardize: every page has one <h1>, each major section has an <h2>, sub-sections use <h3>. BriefingSection's title prop should render as <h2> (or accept a heading-level prop).

Chart accessibility

The SVG sparklines and history chart have no text alternatives. Add role="img" and aria-label to each SVG describing the trend ("FCR trend over 4 weeks: improving from 72% to 81%"). For the larger MetricHistoryChart, also provide a visually-hidden data table as an alternative.

Focus management

When a filter chip is selected on the Team page, focus should remain on the chip group, not jump. When tab content changes, the content panel should not steal focus. These are standard Radix behaviors but verify they work correctly.

Color independence

Status badges use both color and text labels—correct. Trend indicators use both color and icon direction—correct. Sparklines use only color to indicate improving/declining. Add a secondary cue: a small dot or arrow marker at the end of the sparkline path to indicate direction independent of color.

Contrast

The current OKLCH values need verification against WCAG 2.1 AA (4.5:1 for normal text, 3:1 for large text). Specifically check: --muted-foreground on --background, and status colors on their tinted backgrounds. OKLCH perceptual uniformity helps, but verify the actual ratios.

14

Performance Strategy

Current architecture (what's right)

  • All four pages are async Server Components. No client-side data fetching. This is the correct foundation.
  • Only 4 of 20 components are client-side ("use client"). The client bundle is minimal.
  • The N+1 query issue was fixed (batched queries). Database access is efficient.
  • Charts are pure SVG, rendered server-side. No charting library in the client bundle.
  • Manager-facing pages read Cadence-owned data only; no vendor API calls at render time.

What to improve

Suspense streaming

Each page currently awaits all data before rendering anything. The Home page makes 8+ database calls before returning any HTML. Split each page into a fast header section (greeting, employee identity) and slower data sections (metrics, briefings) wrapped in <Suspense> with skeleton fallbacks. This gives the manager visible structure within the first paint.

React cache() for request deduplication

Multiple components on the same page call auth() and getEffectiveManagerContext(). The layout calls them, then the page calls them again. Wrap these in React's cache() to deduplicate within a single request. This is free performance.

Static shells

The sidebar navigation, logo, and layout chrome are the same for every request. Consider extracting the outer shell as a static layout with the dynamic content area as the streaming target. Next.js App Router already does this with nested layouts, but verify the sidebar isn't re-rendering on every navigation.

Image optimization

If employee photos are ever added, use next/image with proper sizing. For the HungerRush logo in the sidebar, use an inline SVG (no network request).

Database indexing

Verify indexes exist on: metric_values(employee_id, metric_definition_id, period_start), meeting_references(manager_user_id, employee_id, scheduled_start), context_items(employee_id, occurred_at). These are the hot query paths for the manager-facing pages.

What to avoid

  • Do not add client-side state management (Redux, Zustand, etc.). Server Components eliminate the need.
  • Do not add a client-side caching layer (SWR, React Query). Data is server-rendered and fresh on each page load.
  • Do not add prefetching beyond what Next.js Link provides by default. The navigation is shallow enough that prefetching adds complexity without measurable benefit.
  • Do not add a service worker. This is a data-fresh application, not an offline-first one.

Visualization Strategy

Charts in Cadence answer specific manager questions. Every chart must justify its existence by naming the question it answers.

Sparklines (TrendSparkline)

Question: "Is this metric getting better or worse over the last few weeks?"

Used in: Team table rows, Employee performance metrics table, Home team performance table.

Current implementation is correct: a 4-point SVG path colored by trend direction. Increase width to 96px for better readability. Add an endpoint dot (already present) and consider adding a very faint fill below the line to increase visual weight.

Historical chart (MetricHistoryChart)

Question: "How has this metric moved over the past 12 weeks relative to its target?"

Used in: Employee page, one chart.

Current implementation is a 640x220 area chart with a dashed target line. This is the right format. Add: hover tooltips with period + value, a metric selector dropdown, and subtle gridlines for the Y axis. Keep the area fill but reduce its opacity slightly (currently too prominent).

Visualizations to avoid

  • Pie/donut charts for status distribution. The stat cards communicate this more effectively and take less space.
  • Bar charts for metric comparison across employees. The table is the better format for comparison.
  • Gauges or radial progress for target attainment. Status badges communicate on/off target more efficiently.
  • Stacked area charts for team-level trends. Too complex for a quick-scan briefing.

Charting library decision

Stay with pure SVG. The visualization needs are simple (sparklines + one area chart with hover). A charting library (Recharts, Chart.js, Nivo) would add 30-100KB to the client bundle for features Cadence doesn't need. The current pure-SVG approach renders server-side, loads instantly, and has zero client-side JavaScript cost for the sparklines. Only the MetricHistoryChart needs a thin client wrapper for tooltip hover tracking.

Future-Proofing Strategy

Variable metric counts

A team might have 3 metrics or 12. The layouts must work for both. The current approach (rendering a table with one row per metric) handles this naturally. The Home page's team performance table, the Employee page's performance metrics table, and the 1:1 Prep's "What Changed" list all use this pattern correctly. No changes needed here.

Variable metric types

Metrics can be percentages, durations, counts, or ratings. The MetricValue component handles formatting based on valueType and unit. This is correct. Ensure sparklines and the history chart work with all value types (they currently assume numeric values, which is fine since all metric types are numeric).

Multiple teams per manager

The current implementation already handles this: Home shows all teams, Team shows per-team sections. If a manager gains a third team, no code changes are needed. The Team selector (recommended above) should appear only when the manager has >1 team.

Additional data sources

New sources produce new NormalizedFacts, which produce new MetricDefinitions and MetricValues. The UI consumes these through the same domain queries. No UI changes needed for a new source. The Data Health page already shows per-source sync status.

What to avoid building now

  • A configurable dashboard layout. Cadence has 4 fixed experiences, not a drag-and-drop dashboard builder.
  • User-customizable metric display order or visibility toggles. This is data-driven through MetricAssignment, not a UI preference.
  • A theme editor or white-labeling system. The HungerRush brand is the brand.
  • Multi-language support. English only for the pilot.

Recommended Frontend Architecture

Keep: Server Components by default

The current architecture is correct: all four pages are async Server Components. Only interactive elements (filter chips, search, tabs, chart tooltips) need "use client". This minimizes the client bundle and ensures fast page loads.

Keep: Tailwind v4 with CSS custom properties

The token system through @theme inline is the right approach. No tailwind.config.ts needed. All theme tokens flow through CSS custom properties.

Keep: Pure SVG charts

Sparklines render server-side with zero client JavaScript. The history chart needs a thin client wrapper for tooltips but no charting library.

Add: Suspense boundaries

Each page should be split into a fast static shell (header, navigation chrome) and streaming data sections. Skeleton fallbacks should match the final layout dimensions closely so the page doesn't reflow when data arrives.

Add: React cache() for auth deduplication

Wrap auth(), getEffectiveManagerContext(), getAssignedTeams(), and getAssignedEmployees() in React's cache() function. This deduplicates calls within a single request without adding a caching layer.

Add: URL-based state for all user-facing selections

Period selection, team selection, and filter state should use URL query parameters, not React state. This makes the state shareable, bookmarkable, and compatible with Server Components. The current period toggle on the Employee page already does this correctly (?period=this_week). Extend the pattern.

Component file organization

The current flat src/components/ directory with 20 files is manageable but getting large. Recommended structure:

  • src/components/ui/ — shadcn primitives (button, card, tabs, avatar, etc.)
  • src/components/ — domain components (StatusBadge, TrendSparkline, MetricValue, etc.)
  • Keep it flat within each directory. Don't create nested subdirectories for 20 files.

What not to add

  • No CSS-in-JS. Tailwind + CSS custom properties is the system.
  • No component library beyond shadcn/ui + Radix. The component count is small enough that bespoke components are better.
  • No Storybook. The component set is small and each component is used in only 1-3 places. Direct page testing is more valuable.
  • No design-token build pipeline (Style Dictionary, etc.). CSS custom properties are the pipeline.

Risks and Potential Over-Engineering

Risk: Spending too much time on dark mode

Dark mode is a real need but a significant token-design effort. Recommendation: define the dark palette now (it's part of the token system), implement it, but don't spend time polishing edge cases until the pilot managers actually request it. The token architecture supports it; the visual refinement can come later.

Risk: Building the "Metrics View" tab on the Team page

The mockup shows an alternate table view. For two 12-person teams with 5 metrics each, this view adds complexity without proportional value. Defer until a manager asks for it or the team sizes grow.

Risk: Over-investing in responsive mobile layouts

The product spec explicitly says "Not a mobile app" and "desktop-first." Make the tables scrollable and the layout stack on small screens, but don't spend significant effort on mobile-specific interactions. A manager opening this on their phone should see a usable layout, not a redesigned experience.

Risk: Adding a notification system

Nothing in the mockups or product spec suggests notifications. Don't build alerts, badges, or real-time updates. The sync is manual; the data is weekly.

Risk: Premature component abstraction

Some components appear similar across pages (MetricChangeRow on Employee and 1:1 Prep) but have subtle differences in layout and information density. Extract only when you've confirmed the API is truly shared. Two pages with slightly different inline JSX is better than a component with 8 props and 3 render modes.

Risk: Chart interactivity scope creep

Adding hover tooltips to the MetricHistoryChart is justified. But don't then add: zoom, pan, date range selection, comparison overlays, or CSV export. The chart answers one question (12-week trend vs target). Keep it focused.

Final Recommended UX Direction

Cadence is a briefing tool, not a dashboard. The mockups correctly establish this with their calm density, clear hierarchy, and meeting-oriented 1:1 Prep page. The current implementation has the right information architecture but needs a visual refinement pass to reach the quality the mockups promise.

The work is a refinement, not a redesign

No pages need to be torn down and rebuilt from scratch. The changes are:

  1. Tighten the typography scale and apply it consistently
  2. Match the mockups' spatial rhythm (more section breathing room, tighter internal density)
  3. Polish components to match mockup quality (larger stat cards, wider sparklines, better hover states)
  4. Add brand presence to the sidebar (logo + wordmark)
  5. Widen the Employee page to a two-column layout
  6. Add period navigation to Home and extend the Employee period selector
  7. Add team summary stats above the Team table
  8. Add Suspense boundaries for progressive loading
  9. Add a dark mode token set
  10. Add a metric selector to the history chart

The information architecture, authorization model, domain layer, and data flow are all correct and should not change. The frontend refinement is purely visual and interactional.

Guiding principle

When in doubt about a design decision, ask: "Does this help a manager prepare for a 1:1 faster?" If the answer is no, don't build it. If the answer is "maybe," defer it until a pilot manager asks.

Decisions I Recommend We Lock In

  • ✓ Server Components for all four pages. No client-side data fetching. Interactive elements (filters, search, tabs, chart tooltips) are the only client components.
  • ✓ Pure SVG for all charts. No charting library. Sparklines render server-side. History chart gets a thin client wrapper for tooltips only.
  • ✓ URL-based state for all selections. Period, team, and filter state use query parameters, not React state. Shareable and Server Component-compatible.
  • ✓ Employee page uses two-column layout at lg+ breakpoints, matching the mockup. Single column below that.
  • ✓ 1:1 Prep is the highest-priority visual refinement target. It's the page that directly saves manager time and has the most room for polish.
  • ✓ Brand treatment in sidebar: HungerRush logo + wordmark + "CADENCE" sub-brand. No more plain-text "CADENCE" alone.
  • ✓ Border radius: 6px (0.375rem) for cards and containers. Current 8px is slightly large for the professional aesthetic.
  • ✓ No page-load animations, counter-up effects, or chart draw sequences. This is a work tool. Instant rendering.
  • ✓ Suspense boundaries on every page for progressive loading. Skeleton shapes match final layout.
  • ✓ Back-link navigation at the top of pages (above the title), not in the footer. Matches the mockup and standard SaaS convention.
  • ✓ React cache() for auth/context deduplication. Free performance, no downside.
  • ✓ Hover state on Team table rows. Subtle background change signals the row is clickable.

Decisions That Should Remain Flexible

  • ? Dark mode polish level. Define the token palette now, implement the basics, but don't spend time perfecting every edge case until a pilot manager requests it.
  • ? "Metrics View" tab on Team page. The mockup shows it but the pilot may not need it. Build the Overview tab well; add Metrics View only if a manager asks for cross-employee metric comparison.
  • ? Period navigation on Home page. Left/right arrows for week navigation are shown in the mockup. Useful, but the weekly briefing is naturally "this week." Build it if straightforward; don't over-invest in historical browsing.
  • ? Meeting prep checklist persistence. localStorage is simple but the feature itself may not matter. Build it with localStorage, observe if managers use it, and decide whether server persistence is needed later.
  • ? Suggested questions styling. The right visual weight depends on how relevant the rule-generated questions actually are for pilot managers. Start with a subtle treatment and promote it if the content proves valuable.
  • ? Sidebar collapse behavior at tablet widths. Icon-only vs. hamburger depends on how managers actually navigate. Start with icon-only collapse; switch to hamburger if testing shows confusion.
  • ? Export functionality. Not in the MVP spec. If a manager asks to export their team data, build it then. Don't pre-build.
  • ? Component extraction threshold. Extract components (MetricChangeRow, ContextTimeline, EmployeeCard) only when the pattern is used identically in 2+ places. Premature extraction creates rigid APIs.

Implementation Order

Start with the foundation (tokens and components), then move outward to individual pages. The 1:1 Prep page is the highest-value refinement target and should come before the others.

  1. Design token refinement + dark mode palette
    Typography scale tokens, spacing tokens, reduced border radius, surface-raised token, complete dark-mode token set in globals.css. Reduced-motion media query.
    Every subsequent phase depends on these tokens being right. Changing tokens after pages are built means re-verifying everything.
  2. Component polish
    StatCard (larger, mockup proportions), TrendSparkline (96px width, area fill), StatusBadge (verify sizing), MetricHistoryChart (hover tooltip), DataFreshness (sync-error awareness). Extract MetricChangeRow if pattern is identical on Employee and 1:1 Prep.
    Polished components make every page better without page-specific work.
  3. Application shell + sidebar
    HungerRush logo in sidebar, active-state refinement, nav reorganization (primary/secondary split), content-area padding adjustment, breadcrumb-at-top pattern.
    The shell wraps every page. Getting it right first makes individual page work look better immediately.
  4. 1:1 Preparation page
    Visual tone shift (calmer, meeting-focused), At a Glance card with trend icon, column layout refinement, "Open Rippling" in header, checklist with localStorage, suggested questions subtle treatment.
    Highest product value. This is the page that directly reduces manager prep time.
  5. Employee page
    Two-column layout, extended period selector (4 options), metric selector for history chart, context tabs refinement, provenance footer with Employee ID + Hire Date.
    Second most detailed page. The manager needs this to understand individual context before preparing for the 1:1.
  6. Team page
    Team summary stats bar, table row hover states, larger avatars, row-click navigates to Employee (arrow to Prep), conditional team selector.
    The comparison layer. Most of the heavy lifting was already done in Phase 2 (component polish).
  7. Home page
    Wider container, stat card polish, employee avatars in attention/improvement cards, team performance table styling, optional week navigation.
    Home is the entry point but benefits most from the component improvements done in earlier phases. Much of the visual improvement comes "for free" from Phases 1-2.
  8. Suspense + performance + accessibility
    Add Suspense boundaries to all four pages, React cache() for request dedup, aria-label on charts, heading hierarchy audit, contrast verification, focus-visible ring, chart color-independence.
    Performance and accessibility are production requirements but benefit from all pages being stable first. Doing this last avoids rework when layouts change.
Time estimate

At the current pace, this is roughly 4–6 working sessions. Each phase is a committable unit that passes typecheck/lint/build. The phases are ordered so each one is useful independently—if the pilot launches after Phase 4, the 1:1 Prep page and component system are polished, which is the highest-value outcome.
