6. Exact CSAT Failure

Root cause: The Zendesk /satisfaction_ratings.json API returns zero results for every queried time window. All 144 csat_summary source records have csatScore: null and totalRatings: 0.

Classification: Source/API Limitation — not a pipeline bug.

Trace

  1. Zendesk API request: GET /satisfaction_ratings.json?score=received&start_time={epoch}&end_time={epoch}
  2. Pagination: Correct — follows next_page in a while loop. But loop never executes because the first response has zero results.
  3. Time window: start_time = Monday 00:00 UTC, end_time = min(Sunday 23:59:59 UTC, now - 90s). Arithmetic verified correct.
  4. Employee attribution: Never reached — zero ratings to attribute.
  5. SourceRecords created: 144 records (36 employees × 4 weeks) all with null csatScore. Hash-based dedup correctly skips on re-sync.
  6. NormalizedFacts: normalizeRecords checks if ("csatScore" in payload && payload.csatScore != null) — correctly skips null scores. Zero facts created.
  7. MetricValues: Zero — no facts to aggregate.
  8. UI: Shows "No Data" correctly (not fabricating a zero).

Most likely explanations

  1. CSAT surveys not enabled in the HungerRush Zendesk instance. The satisfaction_ratings endpoint returns an empty list when surveys are off.
  2. Surveys enabled but no responses in the queried 4-week window.
  3. score=received filter may be excluding results. This parameter filters for ratings that have been submitted (good/bad). If the Zendesk instance uses an alternative satisfaction mechanism, this filter may not match.

Required investigation

External Infrastructure Decision Check the Zendesk admin panel: Admin > Manage > Satisfaction. Confirm whether customer satisfaction ratings are enabled. If enabled, check whether any ratings exist in the Zendesk reporting UI for the same time period. This is not an engineering question — it requires Zendesk admin access.

8. Business-Definition Gaps

Business Definition Required Productivity %

What is the formula? Tickets per hour? Per scheduled hour? Per online hour? This requires a denominator from either the phone system or scheduling system.

Business Definition Required Cases Solved per Day

What is the denominator? Calendar days? Working days (M-F)? Scheduled days? Days with at least one login? The metric value changes significantly depending on the answer.

Business Definition Required Worked Elevated Tickets

What defines "elevated"? Options: Zendesk ticket priority field (urgent/high), a custom field, a specific tag, a specific group/form. Needs a concrete Zendesk field mapping.

Business Definition Required Avoidable Worked Elevated Tickets

What defines "avoidable"? This requires a classification scheme — a tag, a custom field, or a post-hoc manager judgment. Cannot be computed automatically without a classification source.

Business Definition Required First Contact Resolution (FCR)

A metric definition row exists (first_contact_resolution) but there is no Zendesk native FCR field. Options: single-touch tickets (1 public reply → solved), no reopen within N days, a custom field. Each produces very different numbers. Needs an agreed formula and verification method.

Business Definition Required Phone system identity

Which phone system do POS and Menufy teams use? This gates 31 metrics. Without an answer, no call/availability work can begin.

9. Sync Architecture Findings

SYNC-01 Code Issue No HTTP 429 / rate-limit handling

zendeskGet() throws on any non-2xx status including 429. No retry, no backoff, no Retry-After inspection. A single 429 from Zendesk kills the entire sync run. Zendesk enforces 400 requests/minute on Search API. With 36 employees × 4 weeks × 2 queries each = 288 search requests per sync, plus metric lookups and rating lookups, this is at risk.

SYNC-02 Code Issue No retry on transient errors

Network timeouts, 503s, and connection resets immediately fail the sync. The retryable: true flag is recorded on sync errors but nothing ever reads it to retry.

SYNC-03 Code Issue Full re-fetch every sync

Every daily sync re-fetches the full 4-week window from scratch. The cursor resets to week 0 each time (not loaded from previous run). No use of Zendesk's Incremental Exports API for delta syncing.

SYNC-04 Code Issue No overlap window

Week boundaries are exact. Records updated near the boundary could be missed if the Zendesk updated_at timestamp lags slightly behind the boundary.

SYNC-05 Code Issue Sequential source processing

The cron route processes all data sources one by one. With Vercel's function timeout limits, this could be a concern as sources grow.

SYNC-06 Code Issue Failed sync replaces data with nothing

If a sync fails partway through (e.g., after ingesting some source records but before normalizing), the partial state persists. The status is correctly set to "failed" but previously good metricValues are not protected — the next successful sync overwrites them, but if that also fails, there's no fallback to the last-known-good state.

10. Pagination Risks

PAG-01 Code Issue Assembled /people pagination missing

ensurePeople() and discoverRoster() both use limit: 500 with no next_page handling. Organizations with 500+ Assembled agents will have silently incomplete data.

PAG-02 Code Issue Zendesk Search API 1000-result hard cap

Zendesk returns at most 1000 results per search query. Per-agent weekly queries are unlikely to hit this, but there is no detection or warning if truncation occurs.

PAG-03 OK Zendesk satisfaction_ratings, group_memberships, and show_many

All correctly paginated via next_page / batched ID lists.

11. Idempotency Risks

IDEM-01 Code Issue normalizedFacts are not deduplicated

normalizeIngestedRecords() in sync-engine.ts:217-266 does a plain INSERT for every fact on every sync run. There is no upsert, no dedup check, and no unique constraint on normalizedFacts. Re-running a sync for the same period creates duplicate fact rows.

Currently masked because source_records are deduplicated by hash (unchanged records are skipped), and normalizeIngestedRecords only processes records from the current syncRunId. But if a source record's hash changes (e.g., the Zendesk ticket count changes mid-week), the record is re-ingested with a new syncRunId, and normalization creates new fact rows alongside the old ones.

Impact on calculations: computeMetricValuesFromFacts queries ALL facts matching (organizationId, factType) and groups by (employeeId, periodStart, periodEnd). Duplicate facts for the same period would be aggregated together — doubling sum counts, or averaging with extra weight. For tickets_resolved (sum), a duplicate fact would double the count.

IDEM-02 OK sourceRecords deduplication

Correctly uses (dataSourceId, externalRecordType, externalRecordId) unique index + SHA-256 payload hash. Unchanged records are skipped; changed records are updated in place.

IDEM-03 OK metricValues upsert

Uses onConflictDoUpdate on (metricDefinitionId, employeeId, periodStart, periodEnd) unique index. Re-computation is idempotent at this layer.

12. Timezone / Period Risks

TZ-01 OK UTC throughout

weekDates() in src/lib/utils.ts uses getUTCDay(), setUTCDate() consistently. The Zendesk connector's weekOf() uses the same UTC pattern. No accidental local-timezone drift.

TZ-02 Code Issue Period completeness not tracked

No distinction between OPEN (current incomplete week) and COMPLETE (prior full week) periods. The briefing engine compares partial current-week values against full prior-week values without adjustment. A manager viewing on Tuesday sees "Tickets Resolved declined 70%" because only 2/7 days of the current week have elapsed.

TZ-03 Code Issue Duplicate period logic

weekDates() in src/lib/utils.ts and weekOf() in the Zendesk connector implement the same Monday-Sunday calculation independently. Both are correct but should be consolidated.

13. Identity Risks

ID-01 Code Issue CSAT attribution chain is fragile

CSAT ratings use Zendesk numeric assignee_id. The connector resolves email → numeric ID via /users/search.json with an in-memory cache. If the lookup fails (user not found, API error), ratings for that agent are silently empty — no warning, no sync error logged.

ID-02 Code Issue No UNMATCHED/AMBIGUOUS state tracking

resolveEmployeeId() returns null for unmatched external IDs. Source records with null employeeId are created but silently excluded from normalization (line 235: if (!record.employeeId ...) continue). No record of which external IDs failed to match — they disappear.

ID-03 Info Identity drift acknowledged

A person's email can differ across Zendesk/Assembled/Entra. The external_identities table correctly maps each system independently. The system does not guess one system's email from another's.

14. Calculation / Aggregation Risks

CALC-01 Code Issue Team aggregation uses unweighted mean for rates and percentages

getTeamMetricTrend() and generateTeamBriefing() both compute values.reduce(sum) / values.length for all metric types. For CSAT (percentage), Avg Handle Time (duration), etc., this produces meaningfully wrong team averages when employees handle different volumes.

Example from golden dataset: Alice handles 5 tickets at 40min AHT, Bob handles 500 tickets at 8min AHT. Unweighted mean = 24min. Volume-weighted = ~8.3min.

CALC-02 Code Issue "latest" aggregation depends on insertion order

aggregateSourceValues(..., "latest") returns values[values.length - 1]. Facts are returned from the DB in insertion order (no ORDER BY). A bulk re-import that inserts rows out of order would silently change the "latest" value. Currently affects backlog_count only.

CALC-03 Code Issue computeChanges labels 0→N as "stable"

Division-by-zero guard at generate.ts:53: if previousValue === 0, changePercent stays null and direction is "stable". A metric going from 0 to 100 is labeled "stable" rather than showing improvement.

CALC-04 Code Issue computeChanges labels null current as "new"

When currentValue is null but previousValue exists, direction is "new" (suggesting the metric just appeared) rather than something like "missing" or "no_data".

CALC-05 Code Issue Observations pipeline disconnected

detectObservations() exists and works, but is never called from the sync pipeline. The metricObservations table is always empty. Observations shown on the 1:1 page come from computeChanges() in the briefing engine, not from persisted observations.

CALC-06 Code Issue evaluateChangeStatus treats neutral metrics as regressions

The "neutral" direction is not explicitly handled. Any neutral metric with a change >= 1% will be classified as warning or off_target.

15. Target Risks

TGT-01 Code Issue evaluateStatus: 3 dormant bugs (documented in tests)
  • maximum + higher_is_better: both direction branches produce identical logic. Unreachable with current data.
  • exact target type: treated identically to minimum — no equality check.
  • range target type: falls through to no_target. No range logic exists.

All three are documented in src/__tests__/target-resolution.test.ts as known architecture gaps.

TGT-02 Code Issue roleKey always null

resolveTarget in queries.ts:145 passes roleKey: null. Role-based targets are wired in the schema and scoring logic but never activated.

TGT-03 Code Issue No effective-dating enforcement

metricTargets has effective_from / effective_to columns, but target resolution does not filter by date. Changing a target today silently changes the historical status evaluation for past periods.

16. Database / Query Risks

DB-01 Code Issue No cascade deletes

All FKs use ON DELETE no action. Seed cleanup requires manual ordering of 15+ deletes. Production data cleanup would be similarly error-prone.

DB-02 Code Issue No retention policy for sync_runs / sync_errors

These tables accumulate indefinitely. With daily syncs, sync_runs grows by 3+ rows/day (one per source) with no cleanup.

DB-03 Code Issue contextItems table has no producer

The context_items table exists (migration 0003) but no connector or action writes to it. "Previous Context" in the 1:1 page will always be empty.

DB-04 Code Issue force-dynamic on root layout

export const dynamic = "force-dynamic" disables all Next.js static caching. Every page view runs full DB queries. Acceptable at current scale but will need caching for growth.

DB-05 Code Issue Metrics fetched twice in 1:1 page

generateOneOnOne() internally calls getEmployeeMetrics(), and the page also calls getEmployeeMetrics() directly. Same query runs twice per page load.

17. Proposed Schema Changes

New: normalizedFacts dedup constraint

Add a unique index on (employee_id, fact_type, period_start, period_end, data_source_id) and switch the insert to an upsert. This is the single most important schema change — it prevents the duplicate fact accumulation in IDEM-01.

New: period completeness column on metricValues

Add period_status text NOT NULL DEFAULT 'complete' to metricValues with values open | complete | revised. This enables TZ-02 (distinguishing partial from complete periods).

New: metric provenance enhancement

Expand provenance_json on metricValues to store { sourceStrategy, factCount, calculationType, calculationVersion }. For ratio metrics, store numerator/denominator.

Modify: metricDefinitions aggregation_type

The column exists but is nullable and unused. Populate it with the team-level aggregation method (sum | simple_average | weighted_average | recalculate_from_facts | latest | not_applicable) so team aggregation is configuration-driven.

Optional: sync checkpoint table

A sync_checkpoints table storing the last safe checkpoint per data source for incremental sync. Not required if we keep the 4-week full-refresh model (which is pragmatic for the current scale).

18. Proposed Sync Changes

Priority 1: Rate-limit handling (SYNC-01, SYNC-02)

Wrap zendeskGet() and assembledGet() with a retry layer: exponential backoff (1s, 2s, 4s), max 3 retries, respect Retry-After header on 429. Distinguish transient (429, 500, 502, 503, 504, network errors) from permanent (401, 403, 404) failures. Record retry count in sync_runs.metadata_json.

Priority 2: Fact deduplication (IDEM-01)

Two options (propose option A):

  • A: Delete existing facts for the affected (employeeId, factType, periodStart, periodEnd, dataSourceId) before inserting new ones in the same transaction. Simple, correct, no schema change needed.
  • B: Add a unique constraint and use upsert. Cleaner long-term but requires a migration that first cleans up existing duplicates.

Priority 3: Assembled pagination (PAG-01)

Add next_page handling to ensurePeople() and discoverRoster().

Lower priority: Overlap window, incremental sync

At current scale (36 employees, 4-week window, daily sync), the full re-fetch model works. The source record hash-based dedup means unchanged data is skipped efficiently. Overlap windows and incremental cursors become valuable at larger scale.

19. Proposed Metric-Engine Changes

Fix team aggregation (CALC-01)

Use the aggregation_type column on metricDefinitions to drive team-level computation. For percentage/rate metrics, use weighted_average (weight by the denominator, e.g., total ratings for CSAT, ticket count for AHT). For count metrics, use sum. For snapshot metrics (backlog), use sum or simple_average depending on the business definition.

Fix "latest" ordering (CALC-02)

Add an ORDER BY created_at ASC to the facts query in computeMetricValuesFromFacts, or use the fact's source_record_id → source_updated_at as the ordering key.

Fix change detection edge cases (CALC-03, CALC-04)

When previousValue === 0 and currentValue > 0, classify as "improved" (or "new" if there was genuinely no prior period). When currentValue is null but previousValue existed, classify as "missing" or "no_data" rather than "new".

Wire observations pipeline (CALC-05)

Call detectObservations() after computeMetricValuesFromFacts() in both the cron route and manual sync route. Persist results to metricObservations.

Fix evaluateStatus bugs (TGT-01)

Implement correct logic for maximum + higher_is_better, exact target type (equality with tolerance), and range target type (value between min and max). All three are already documented in tests — the tests should be updated to expect correct behavior, then the implementation fixed.

20. Proposed Reconciliation System

A reconciliation system already exists (reconciliation_runs + reconciliation_results tables, engine in src/lib/domain/reconciliation/engine.ts, UI at /reconciliation).

Current state

The existing reconciliation compares metricValues against re-aggregated normalizedFacts. This catches drift between the two Cadence layers but does NOT compare against the authoritative external source.

Proposed enhancement

  1. Source-side reconciliation: For each reconciliation run, fetch fresh counts directly from the Zendesk API (e.g., re-run the search query for a specific employee+period) and compare against the Cadence metricValue. This is the true source-of-truth comparison the spec requires.
  2. Metric-specific tolerances: Ticket counts: 0 tolerance. Percentages: 0.5% tolerance (rounding). Durations: 0.5min tolerance.
  3. Automated scheduling: Run reconciliation for the prior completed week after each sync, not just on-demand.

21. Proposed Explain Metric

Interface

Admin/developer tool accessible via a query parameter or admin-only button on the employee page. Accepts: employeeId, metricKey, periodStart, periodEnd.

Output

A structured diagnostic showing the full pipeline trace for one metric, one employee, one period:

  • Metric definition (key, category, unit, direction, calculationType, sourceStrategy)
  • Assignment (team, display order, isPrimary)
  • Resolved target (value, type, source level, priority)
  • Data source (type, last successful sync, time since sync)
  • Source records (count, qualifying count, employee-matched count)
  • Normalized facts (count, rejected facts with reasons)
  • Calculation (type, input values, result, version)
  • For ratio metrics: numerator / denominator
  • MetricValue (numeric value, quality status, freshness)
  • Observations derived from this metric

Implementation

A server action or API route that queries across metricDefinitions, metricAssignments, metricTargets, dataSources, syncRuns, sourceRecords, normalizedFacts, metricValues, and metricObservations for the specified employee+metric+period. Returns a structured JSON object rendered by a client component. Platform admin only.

24. Migration / Backfill Implications

normalizedFacts dedup cleanup

Before adding a unique constraint, existing duplicates must be cleaned. Strategy: identify duplicate groups by (employeeId, factType, periodStart, periodEnd, dataSourceId), keep the most recent row (by created_at), delete the rest. Then add the constraint. Run this as a one-time migration script, not a Drizzle migration.

metricValues period_status backfill

All existing metricValues can be set to 'complete' since they're for past periods. Only future writes need the open/complete distinction.

Historical backfill

If the sync is enhanced with deeper history (beyond 4 weeks), implement as a separate idempotent script that processes one week at a time with progress tracking. Must not interfere with daily live sync.
